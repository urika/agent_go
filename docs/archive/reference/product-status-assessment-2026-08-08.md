# agent_go 产品现状评估

> 评估日期：2026-08-08
> 评估视角：产品目标，而非单纯工程任务完成度

## 一、最终产品目标

agent_go 的最终产品目标是：

> 用户输入一次开发任务，agent_go 最终交付一个可审查、可合并的 PR。

产品不仅要能够执行代码修改，还要能够保证：

- 成功和失败状态可信。
- 失败原因可定位。
- 代码变更不会丢失或混入其他任务。
- 用户可以恢复、审查或重新交付。
- 最终产物能够被用户明确取得并合并。

## 二、当前阶段判断

当前产品处于：

```text
可靠执行平台（Execution Platform）
尚未达到可靠 PR 交付产品（Reliable PR Delivery Product）
```

从最终产品目标看，整体完成度可粗略估计为 **60% 左右**。这不是精确 KPI，而是用于判断产品阶段的定性估计；各能力成熟度并不均衡。

## 三、能力成熟度

| 能力 | 当前程度 | 产品评价 |
|---|---:|---|
| 任务理解、Plan 和拆解 | 较高 | 核心流程已建立 |
| 子任务隔离与并发执行 | 较高 | worktree、DAG 和波次调度较完整 |
| 验证、重试和失败分类 | 较高 | 已具备工程化基础 |
| 成本和指标度量 | 较高 | M0 契约、Schema、报告和批次治理已建立 |
| Accepted Delivery 判定 | 中等 | 判定逻辑存在，但依赖真实交付产物 |
| delivery branch 汇总 | 较低 | 属于 M1 核心缺口 |
| PR head/base 管理 | 较低 | 尚未形成完整交付闭环 |
| 交付失败后的独立恢复 | 较低 | 尚不能完全脱离 Agent 重跑 |
| 真实用户和真实仓库验证 | 较低 | 当前主要是 mock、fixture 和最小 E2E |
| 正式产品基线 | 未完成 | 尚缺一批新的固定 baseline 数据 |

## 四、当前已经具备的产品能力

当前适合用于：

- 将复杂任务拆成多个隔离子任务。
- 按依赖关系执行并行或串行任务。
- 自动运行验证并进行有限重试。
- 记录成本、失败原因、模型和任务版本。
- 判断任务是否达到 Accepted Delivery 条件。
- 保留失败现场并支持恢复、审查和重放。
- 对 Bench 结果进行 schema 校验、批次隔离和指标冻结。

这些能力已经明显超过简单调用 Claude CLI 的脚本，具备可靠执行平台的基础。

## 五、当前不能稳定承诺的产品能力

当前还不能对用户稳定承诺：

- 每次任务都自动产出一个可合并 PR。
- 多个子任务一定会汇总到唯一 delivery branch。
- PR 创建失败后可以只重试交付而不重新执行 Agent。
- 用户不需要人工处理分支、合并和交付异常。
- 当前 Bench 数据足以支撑正式模型排名或产品 KPI 决策。

## 六、最大产品缺口

当前最关键的缺口不是继续增加评估字段，而是完成交付闭环：

1. 创建唯一的 delivery branch。
2. 汇总所有必要子任务 commit。
3. 明确 target branch、PR base 和 PR head 的关系。
4. 真实创建 PR，并持久化 PR 信息。
5. PR 创建失败后支持独立重试交付。
6. 使用真实仓库完成端到端交付验证。

## 七、M0 现状

M0 的产品契约和度量基础设施已经基本完成：

- Accepted Delivery 契约已冻结。
- 状态机已统一。
- Failure Class 已统一。
- Bench Schema、Suite 和任务版本已冻结。
- 指标公式和 Metric Freeze 报告已实现。
- 结果批次治理和最小 E2E 门禁已实现。
- 全量测试通过：`1864 passed`。

但 M0 仍有一个正式完成门禁未满足：

- 尚未生成一批新的正式固定 baseline 数据。

历史 `results_v1/v2/v3/v4` 数据只能作为 exploratory 数据，不能替代正式产品基线。

## 八、产品阶段结论

当前阶段应定义为：

```text
M0：产品契约和度量基础设施基本完成
M1：交付闭环待实施
产品状态：Pre-Delivery
```

下一阶段应优先完成 delivery branch、commit 汇总、PR head/base、交付失败恢复和真实 Git/PR 端到端验证。完成这些能力后，产品才可以从“能够执行并解释失败”进入“能够稳定交付结果”。
