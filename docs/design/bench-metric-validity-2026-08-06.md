## 结论先行

当前 bench 指标体系存在三处「设计缺陷」级别的硬伤，导致 **v3 的 34% 通过率有一半是测量假象（真实约 67%）**。这套数据**目前不能直接作为战略决策依据**，但「方向性结论」可用，需降级使用。本文把每个问题按根因（指标设计 / 数据 / 评测工具漂移）归类，给出量化证据、产品视角解读，以及升级为可信决策依据的修复路径。

此外，第四节是一个专题深挖：**timeout 与通过率的矛盾根因不是"卡得太紧"，而是"控制变量指错方向"**——timeout 按子任务数分配时间，但实际耗时由难度驱动，且 kill 把已完成任务计为失败。这是连接"成本控制"与"通过率"的最关键触点，单独成节。

## 一、指标度量有效性诊断

证据全部来自 `bench.py` 源码 + 数据交叉验证。

### A. 指标设计缺陷（最严重，直接影响决策）

#### 缺陷 1：`binary_pass` 与 `pass_rate` 计算时序错位 + `all([])` 空真值陷阱 → binary_pass 不可信

源码 `bench.py:746-769` 的执行顺序是：先算 `all_passed` → 立刻算 `binary_pass` → **之后**（785 行起的 aborted 分支）才把 `completed=0`、`all_passed=False`。于是 `binary_pass` 冻结在中止修正**之前**的值，而 `pass_rate` 用的是修正**之后**的值，两者必然矛盾。再叠加 `all(r.verify_ok for r in results if status=='completed')` 在「零个子任务 completed」时返回 `all([])==True` 的 Python 陷阱，结果是：

| 版本 | completed=0 但 binary_pass=True | 占比 |
|------|------|------|
| v2 | 0 | 0% |
| v3 | **109 / 198** | **55%** |
| v4_calib | 9 / 54 | 17% |

**超过一半的 v3 记录里，"全子任务失败"和"binary_pass=True"同时成立。** binary_pass 当前不表达"任务通过"，不能用作任何门禁或 KPI。

> 根因定位（`bench.py`）：
> - `all_passed = all(r.get("verify_ok", False) for r in results if r.get("status") == "completed")` —— 空迭代器 → `True`
> - `binary_pass = all_passed and (semantic_pass is not False)` —— 在 aborted 分支之前冻结
> - aborted 分支随后 `completed = 0; all_passed = False`，但**不回写 binary_pass**

#### 缺陷 2：$/pass 的分母把「部分完成」当成「等效完全通过」，概念错误

PRD（§产品 KPI，533-536 行）把 $/pass 定义为 `Σcost / Σpass_rate`，含义是"获得一个等效完全通过的成本"。但 pass_rate 是 `completed/total_subtasks`，于是一个 4 子任务依赖链只跑完 1 个，会被记为 0.25 个"等效通过"。

而 agent_go 的子任务是 **upstream→downstream 有序依赖**（PRD 原则 2「上下文隔离」、架构的 `git merge upstream` 传递），下游被 blocked 时，1/4 完成 = **0 个可交付物**，不是 0.25。

| 版本 | 部分完成记录（pass_rate ∈ {0.25,0.33,0.5}） |
|------|------|
| v3 | 17 条 |
| v4_calib | 3 条 |

这些记录系统性低估真实单交付成本。这是定义层面的概念缺陷，PRD 继承了它。

#### 缺陷 3：`pass_rate` 分母不稳——`total_subtasks = len(results)`（已落盘的），不是计划数

任务被 SIGKILL 时若 meta 还没写 results，分母直接消失：

| 版本 | total_subtasks=0 记录 |
|------|------|
| v2 | 0 / 198 |
| v3 | **21 / 198** |
| v4_calib | 0 / 54 |

这些记录 pass_rate 被强制置 0，但我们连"原计划几个子任务"都不知道。它们是**不可测**，不是"失败"，却被当成失败计入分母。

### B. 数据问题（可清洗，但当前未隔离）

#### 问题 4：37% 的 v3 记录是「假失败」——子任务全部完成且 verify_ok，只因收尾阶段超时被 zeroed

把缺陷 1 的反面量化后得到的杀手级证据：65 条记录的 `per_subtask` 显示**每个子任务都 status=completed 且 verify_ok=True**，但顶层 pass_rate=0，因为它们 `timed_out=True`、撞上了 aborted 分支的"中途被杀→completed=0"逻辑（实际多数是收尾阶段被杀）。

| 口径 | v3 通过记录 | 通过率 |
|------|------------|--------|
| 当前 headline（pass_rate>0） | 68 / 198 | **34%** |
| 修正后（计入已完成已验证的假失败） | 133 / 198 | **~67%** |

> 65 / 177 条有 per_subtask 的 v3 记录属于此类（全部 timed_out）。

**上游数据分析里"v3 通过率塌到 30%、驱动 v4 重新校准"的核心叙事，有一半是测量假象。** 真实 v3 通过率接近 67%，和 v4_calib（80%）的差距远没有看上去那么大。这意味着 v4 的 recalibration 可能在"纠正一个被夸大的问题"。

> 这 65 条假失败全部 `timed_out=True`——它们是"timeout 与通过率矛盾"的度量层根源，根因深挖见**第四节专题**。

#### 问题 5：20-24% 的记录 cost=0（API/本地/故障），全部 pass_rate=0，把基础设施故障误计为模型/产品失败

| 版本 | cost=0 记录 | 其中 pass_rate>0 |
|------|------------|------|
| v2 | 40/198 (20%) | 0 |
| v3 | 47/198 (24%) | 0 |
| v4_calib | 3/54 (6%) | 0 |

成本侧 `avg_cost_usd` 正确排除了它们（只算 >0），但通过率侧把它们当失败计入了分母。**这把"API 可用性/限流"和"模型能力"混为一谈**——恰恰违反了 PRD 反指标表的初衷（"省钱产出垃圾" vs "基础设施抽风"是两回事）。

### C. 评测工具漂移（跨切面，最隐蔽）

#### 问题 6：v1 / v2 / v3 / v4 是四把不同的尺子，但被当成连续时间线比较

- v2：无 per_subtask、无语义判官、无 aborted 分支（旧采集器）
- v3：引入语义判官 + K1"收尾被杀"处理（新采集器）
- v4：在 v3 基础上调 timeout
- **旧 PRD 的 KPI 基线（K8=88.9% 🟢达标）曾钉在 Bench v1**（332 条，又一个采集器）；该结论现已降级为历史 exploratory 结果。

直接后果：PRD 写"K8 首次通过率 88.9%🟢达标"，但同一指标在 v3 上用当前代码复算是 **58.8%**。"达标"与否取决于用哪把尺子。KPI 看板是绿的，但绿得很脆弱。

## 二、产品问题（PM 视角，对照 PRD）

**1. 度量层违背了 PRD 第一原则（#4「人的注意力是最稀缺资源 / 异常下钻」）。** 系统现在向人推送**假异常**（37% 的"失败"其实是已完成）并隐藏真异常（infra 故障混在能力失败里）。对一个"关掉终端、回来看结果"的异步委派产品，**信任契约的根基是"失败信号可信"**——目前不成立。这是 P0 级产品风险，不是 P2 体验问题。

**2. 战略决策被建立在失真的仪表盘上。** S10 成本控制（v3 默认开启 57% 超时）+ v4 recalibration，这条调整链的**触发依据**（v3 通过率 30%）有约 37 个百分点的测量误差。方向（成本控制、Sonnet 主力、Opus 降级）大致没错，但**力度可能过冲**——很可能 v3 根本没那么糟，v4 的"大幅回升"部分只是把假失败又算回来了。

**3. KPI 看板与实测脱节（治理债）。** PRD 把基线钉在 v1，代码和数据却已演进到 v3/v4，两者从没对齐过。任何"本季度 KPI 达标了吗"的问答目前都没有可信答案。

## 三、能否作为战略决策依据？

**结论：不能直接作为战略决策依据；但「方向性结论」可用，需降级使用。**

| 用途 | 可信度 | 说明 |
|------|--------|------|
| 模型相对排序（Sonnet > Haiku > Opus 被支配） | 🟡 方向可信 | Opus 被支配在所有口径下都成立；Sonnet vs Haiku 的 11pp 差距在假失败修正后可能缩小，需复核 |
| 绝对 KPI 达标判定（K4 $/pass、K8 通过率） | 🔴 不可信 | 分母/分子都有系统性偏差，且基线钉在另一把尺子 |
| 版本间趋势对比（v2→v3→v4） | 🔴 不可信 | 工具漂移 + 假失败，趋势失真 |
| 单任务难度/成本诊断 | 🟢 可信 | cost-recalibration.md 的"子任务数是第一成本驱动"等结论稳健 |

### 升级为战略决策依据的三个前置条件（即修复优先级）

1. **修指标缺陷**（1-2 天）：`binary_pass` 改为在 aborted 分支之后计算，并修 `all([])` 陷阱（空集应判 False）；`pass_rate` 分母改用计划子任务数而非 `len(results)`；`$/pass` 分母对依赖链改为"全部子任务通过才算 1"。然后用修正后口径**重算 v2/v3/v4 全部 KPI**。
2. **隔离 infra 故障**（1 天）：cost=0 / API 错误 / 超时的记录打 `failure_class ∈ {infra, model, timeout}` 标签，KPI 分母只计 model 类。这一步很可能让"8 个 0% 任务"里的一部分显形为 infra 问题而非能力问题。
3. **冻结基线**（治理）：选一套固定采集器 + 固定 22 任务集作为唯一 KPI 基准，PRD 基线迁到它上面；禁止跨 bench 版本直接比数字，只比同口径内趋势。

**做完这三步之前，建议把当前 bench 结论从"战略决策依据"降级为"假设待验证"**——尤其暂停任何"因为 v3 只有 30% 所以要 X"的决策。模型选型可以保守推进（Sonnet 默认、Opus 降级这条即便数据有偏也站得住），但 KPI 达标状态、成本目标的设定和考核，必须等度量修复后再锁定。

## 四、专题：timeout 与通过率矛盾的根因与策略

timeout 是当前系统最大的失败来源（v3 57% 超时），也是"成本控制"与"通过率"正面冲突的接触面。深挖数据后发现，这个矛盾的根因比"timeout 太紧"深刻得多——**控制变量指错了方向**。

### 矛盾是两个问题被混为一谈

1. **真矛盾（策略层）**：用 timeout 当成本控制手段 → 超时即判失败 → 通过率必然被压。这是真实的成本-质量权衡。
2. **假矛盾（度量层）**：任务其实已经做完，只在收尾阶段被杀，却被计为失败（即第二节"问题 4"的 65 条假失败）。这把矛盾人为放大了约 37pp。

团队看到"57% 超时 → 34% 通过率"并据此做了 v4 重新校准，但反应的对象有一半是假象。

### 根因 A（策略层）：timeout 是"指错方向"的控制变量

`_dynamic_timeout = max(YAML, 子任务数×150 + 120)`（`bench.py:540`）**按子任务数分配时间**——子任务越多给越多。但实际耗时**由难度驱动**（cost-recalibration.md 实测：hard 是 easy 的 4-5×），与子任务数无关。数据印证了这种错配——**超时率与子任务数反相关**，和设计假设完全相反：

| 子任务数 | v3 超时率 |
|---------|----------|
| 0 | 100% (21/21) |
| 1 | 77% (30/39) |
| 2 | 53% |
| 3 | 41% |
| 4 | 16% |

按任务看更清楚：100% 超时的全是低子任务数任务——`add-simple-caching`(0.7 子)、`safe-file-reader`(0.0 子)、`security-hardening-taskmgr`(1.2 子)、`add-caching-layer`(1.6 子)。一个被"欠分解"成 1-2 个长子任务的硬任务，只拿到很短的 timeout（1 子任务仅 270s）就被杀；一个被分成 5 个短子任务的简单任务，反而拿到 870s 宽裕时间早早跑完。**给得多的不需要，需要的给得少。**

这是结构错配而非参数问题——所以 v4 只能靠"逐任务人工校准 YAML timeout"把超时率从 57% 压到 11%，是一条**人工绷带**，对新任务不泛化。

### 根因 B（度量层）：kill 把"已完成"计为"失败"

承接第二节问题 4：65 条 v3 记录的 `per_subtask` 全部 completed + verify_ok，却 pass_rate=0，因为 `timed_out=True` 撞上 aborted 分支被强制 `completed=0`。它们都花了真实成本（$0.006–0.13）、跑了中位 660s——**活干完了，收尾时被杀，账上记零分**。`_run_with_grace` 的 SIGTERM 60s grace 本意是让 agent_go 存 meta 再死，但"收尾被杀→视为完工"的判定要求 results 覆盖全部计划子任务 id，SIGKILL 没存上 meta 就漏判。**结果：超时这个动作，既花了钱、又没拿到产出、还把已完成的产出也抹掉。作为成本控制手段，它是负效的。**

### 根因 C：三种 kill 场景被塞进同一个 `timed_out`

| 场景 | 信号 | 正确处置 |
|------|------|---------|
| 卡死（真卡住无进展） | 0 子任务、plan 已生成但 0 results、空转中位 480s | 该杀 |
| 超预算（钱花超了） | cost 接近 L3 上限 $0.50 | 该优雅降级，不是硬杀 |
| 收尾竞态（已完成，cleanup 被杀） | 全子任务 completed+verified 但 timed_out | **该计为通过** |

当前 `timed_out=True` 把三者一锅端、全判失败，策略无法分别施策。

### 由目标反推策略

目标"预算限制下、高通过率、高效率"的关键约束是**预算，不是时间**。所以第一控制变量必须是预算（cost），timeout 降为安全网。由此（按目标必要性排序）：

1. **预算升为一等信号，timeout 降为安全网（根因 A）。** `config.py` 的 cost_control 三层（L1 单调用 / L3 任务总预算 $0.50）已存在但没当主控。扶正它：每任务带 budget，接近预算时优雅降级（换便宜模型、停重试、收缩范围）而非硬 kill。timeout 只保留一个宽松的、只抓真卡死的安全网。
2. **kill 改为"无进展"触发，而非"墙钟"触发（根因 A/C）。** 正在产出 token/改文件的任务，永远不该因为"太慢"被杀。卡死判定用"N 秒无输出/无文件变更"。这一条直接保住"长但有效"的硬任务通过率——恰是当前被误杀的主力。
3. **时间预算按难度分档，不按子任务数（根因 A）。** 把 `_dynamic_timeout` 的 `子任务数×150` 换成 `难度×基准`，或取两者 max。策略 1/2 的补充。
4. **修度量，三种 kill 分开打标（根因 B/C，且是前置）。** 给每次 kill 打 `kill_reason ∈ {stuck, over_budget, cleanup_race}`；cleanup_race 直接计为通过。这一步先做——它把"57%→34%"的真假分开，团队才能看到真实的 timeout/通过率曲线，进而对策略 1-3 理性调参。
5. **欠分解检测（根因 A 源头）。** 1-2 子任务的硬任务被杀，根子在规划阶段把硬任务欠分解。Plan 阶段加约束：高难度任务若子任务数过低，触发再分解或提升 worker 模型档位。这是 PRD 原则 #5"复杂度判断在规划阶段收敛"的落地——在规划期算清成本/时长预算，而不是等执行期用 timeout 兜底。

**一句话**：timeout 与通过率的矛盾，表面是"卡得太紧"，根因是"控制变量选错 + kill 把完成计为失败 + 三种死法混为一谈"。正解是让预算（不是墙钟）当主控、让无进展（不是时长）触发 kill、先修度量把假矛盾剔掉——把 timeout 从"成本杀手"降级为"卡死安全网"，通过率和效率才能同时保住，预算约束才真正被守住。
