## 2. 修正后的依赖图

### 原计划（线性，有误）
```
Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4
```

### 校准后（并行化，关键路径明确）
```
                    ┌─ P0-1 (消灭 print) ─────────────┐
                    │   └─ 同步修 R3: --quiet 回归     │
                    │                                  ▼
P0-4 (Console 绑定) ┤                           P0-2 (语义方法)
                    │                                  │
                    └─ P0-5 (Plan 紧凑展示) ───────────┤
                                                       │
              ┌────────────────────────────────────────┘
              │
P1-2 (验证卡片) ◀── 独立可做，不依赖 P0，数据已在 executor
              │
P1-5 (stream-json 进度) ◀── 关键路径，解锁 P1-1 + P3-2
              │   ├─→ P1-1 (进度行)
              │   └─→ P3-2 (实时日志)
              │
P0.5 (--json 模式) ◀── 与 P0 同层，Console 第三模式
              │
P0-5 + P2-1 ($EDITOR Plan) ◀── 完整 Plan 交互，一起交付
              │
P3-1 (TUI --interactive) ◀── 依赖 P1 全部 + R1 线程验证
```

**关键路径**：`P1-5 → P1-1 → P3-1`（stream-json 进度是后续两个任务的使能项）

**独立可做**（无前置依赖）：
- P1-2 验证卡片（0.5d）
- P0.5 --json 模式（3d）
- P4-1 执行回放（3d）

## 4. 执行序列

### Sprint 1：即时回报（~1 人天）
| 任务 | 估时 | 验收 |
|---|---|---|
| P1-2 验证上下文卡片 | 0.5d | 验证失败时展示 stderr 尾部 + git diff --stat |
| P0-1a `--quiet` 修复（ui.py 确认菜单） | 0.3d | `--quiet` 下不再空屏，保留单行确认 |

**用户可感知改进**：验证失败不再只显示一行"[C/R/M/A]"，能看到失败原因。

### Sprint 2：基础规范化 + CI 能力（~6 人天）
| 任务 | 估时 | 前置 |
|---|---|---|
| P0.5 --json 全局模式 | 3d | 无 |
| P0-1b 剩余 print 消灭 | 1.7d | 无 |
| P0-2 语义方法激活 | 0.5d | 无 |
| P0-4 Console 绑定统一 | 0.5d | 无 |

**并行**：P0.5、P0-1b、P0-2、P0-4 可四人并行。

### Sprint 3：进度透明度关键路径（~3.5 人天）
| 任务 | 估时 | 前置 |
|---|---|---|
| P1-5 stream-json 进度 | 2d | 无 |
| P1-1 进度行 | 1.5d | P1-5 完成 |

**技术验证（并行）**：
- TUI 主线程 PoC（验证 `_run_pipeline` 移入后台线程 + SIGINT 传递）— 决定 P3-1 是否可行
- PLAN.md 解析器 PoC（5 个边界用例）— 校准 P2-1 工作量

### Sprint 4：Plan 交互完整升级（~6 人天）
