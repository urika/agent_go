# Plan 自优化的产品目标与功能演进分析

> 文档性质：产品讨论稿，暂不作为已冻结的 roadmap 或 PRD 变更
> 状态：待后续讨论
> 日期：2026-08-12
> 关联调研：[Plan 级反馈与受控重规划调研及设计决策](plan-self-optimization-research.md)

## 1. 核心结论

Plan 自优化是 agent_go 的可靠交付支撑能力，但不是产品目标本身。agent_go 的产品目标仍然是：

```text
可信指标
  → 可执行计划
  → 可靠执行
  → 可恢复失败
  → Accepted Delivery
```

当前不应直接实现无限的自动重规划循环。推荐路线是：

```text
Plan 预检
  → 执行前一次自动修复
  → 跨任务 plan_feedback 灰度
  → M3 真实任务 A/B 验证
  → 局部一次性重规划
  → 再评估动态 DAG
```

## 2. 对产品目标的意义

### 2.1 Plan 应成为控制平面

Plan 不应只是 Planner 的文本输出，而应成为可校验、可版本化、可审计的执行契约，至少承担以下职责：

- 需求和验收标准覆盖
- 子任务边界和文件范围
- 依赖关系和执行顺序
- 验证责任
- 权限和预算约束
- 失败后的修订边界

因此，产品能力应从“生成 Plan”提升为“生成并验证可执行 Plan”。

| 现有能力 | 应提升为 |
|---|---|
| Plan 生成 | 结构化计划生成 |
| Plan 确认 | 用户批准的执行契约 |
| Subtask 执行 | 受 Plan 约束的执行 |
| 验证失败 | 有分类的反馈事件 |
| Plan 重新生成 | 有边界的 Plan 修订 |
| 最终交付 | 需求到 PR 的完整证据链 |

### 2.2 可靠性优先于“自我进化”

Plan 自优化的价值必须通过产品结果证明，而不能用“自动重规划次数”或“自动修改成功率”衡量。优先关注：

- Accepted Delivery Rate 是否提升
- Cost per Accepted Delivery 是否下降
- 人工修改 Plan 和恢复任务的时间是否减少
- 同类失败是否减少
- requirement/acceptance 覆盖是否保持
- 失败是否仍然可解释和可恢复

系统不应为了提高 `pass_rate` 而：

- 删除 requirement 或 acceptance criterion
- 缩小任务范围
- 降低验证标准
- 生成更容易通过但不完整的 Plan
- 改变指标分母或失败分类

### 2.3 产品非目标

当前阶段不把以下内容作为产品目标：

- 自动修改 agent_go 自身 harness
- 自动优化 Planner 或“优化 Planner 的 Planner”
- Devin 式无限动态 DAG
- 只追求历史参考值 `$0.05` 或 `K1 >=97%`
- 用自动重规划替代人工架构决策

历史 `97% first_pass` 只是未经 M3 验证的参考目标，不能作为当前冻结 KPI。

## 3. 对现有问题的覆盖

decision-20260812 有 35 条记录、10 条失败。Plan 自优化只应处理属于 Plan 层的问题，不应成为所有失败的统一处理器。

| 问题类型 | 典型现象 | 应处理的层级 | Plan 自优化覆盖 |
|---|---|---|---|
| Plan 确定性错误 | 验证命令不在白名单、文件冲突、依赖环 | 执行前 Plan 预检和一次修复 | 高 |
| 同类错误跨任务复发 | 不同任务反复生成相同不合规命令 | 跨任务 `plan_feedback` | 中高 |
| 上游失败导致下游 blocked | 下游原计划无法继续 | 一次局部重规划 | 中，需后续验证 |
| 模型实现失败 | 验证失败、语义不通过、修复不收敛 | Subtask repair / Reflexion / 人工恢复 | 低 |
| 基础设施失败 | API、依赖、环境、进程不可用 | 超时、降级和进程治理 | 低 |
| 交付失败 | PR、mergeability、merge 冲突 | delivery branch / PR / merge 恢复 | 非 Plan 核心问题 |

此前发现的验证命令问题属于 Plan 确定性错误，包括：

- `python -c` 使用多行、装饰器或 `with`
- 使用 `bash -c` / `sh -c` 包裹命令
- 命令前添加自然语言描述
- 验证命令不在安全白名单

这些问题适合在 Worker 启动前处理，而不适合等到执行失败后再消耗修复重试。

## 4. 功能演进分层

### 4.1 Plan preflight repair：当前优先能力

```text
generate_plan
    ↓
deterministic validation
    ├─ 通过 → confirm_plan → execute
    └─ 发现确定性错误
          ↓
       Planner 修订一次
          ↓
       重新校验
          ├─ 通过 → confirm_plan → execute
          └─ 失败 → 阻断或人工确认
```

适合处理：

- 验证命令安全门禁拒绝
- 文件范围冲突
- 依赖环
- requirement 覆盖不足
- 不可验证的上游步骤
- 明显的过度分解

必须满足：

- 最多自动修订一次
- 修订前后保存 Plan 版本和 diff
- 不得删除或放宽需求、验收、架构约束和验证责任
- 重新执行完整预检
- 修订成本计入任务预算
- 失败后不进入 Worker

这是当前最直接、最容易验证、风险最低的 Plan 层能力。

### 4.2 `plan_feedback`：跨任务防复发能力

```text
任务 A 失败
  → 记录确定性失败模式
  → 规则化建议
  → 注入任务 B 的 Planner
  → 减少同类错误复发
```

适合反馈：

- 验证命令格式错误
- 常见文件范围错误
- 欠分解或过度分解
- 常见依赖遗漏

不能把未经处理的历史错误文本直接注入 Planner。必须具备：

- 仓库或配置作用域隔离
- 原始命令脱敏和截断
- 反馈来源、时间和置信度
- feature flag
- 过期、删除和回滚能力
- A/B 实验

`plan_feedback` 主要防止未来任务复发，不能直接修复已经生成的当前 Plan。因此它不能替代 Plan preflight repair。

### 4.3 局部一次性重规划：后续灰度能力

当某个 Subtask 失败时，只重规划失败 Subtask 和尚未执行的下游步骤：

```text
subtask A 已完成
subtask B 失败
subtask C/D 尚未执行
        ↓
只重规划 B/C/D
不修改 A 的 commit
不重建整个任务
```

适合触发的场景：

- 上游失败导致下游 blocked
- 发现新的必要文件或依赖
- 原 Subtask 作用域不成立
- 原验证与任务目标不一致

不适合触发的场景：

- 模型实现能力不足
- 网络或 API 故障
- 超时但根因不明
- 语义评估单独失败
- 交付分支冲突

必须限制为：

- 最多一次
- 默认人工确认
- 只影响未执行范围
- 不重跑已接受 commit
- 继承原预算、权限、需求和验收约束
- 不允许递归扩大任务图

### 4.4 动态 DAG：远期探索能力

Devin 式持续动态重规划会带来更强的长任务适应能力，但也会改变 agent_go 的核心状态模型：

- 静态波次变为动态调度
- Plan 不再是一次性批准契约
- 已完成 Subtask 的归属需要重新解释
- delivery branch 可能反复重建
- 成本和指标归属复杂化
- 可能出现无限重规划

在以下条件满足前，不应进入关键路径：

- M3 真实任务数据充分
- 局部一次性重规划已验证
- evaluator 误判率可接受
- re-plan 成本可计量
- Accepted Delivery 没有下降
- Plan 版本、预算和回滚协议稳定

## 5. 对功能计划的影响

### 当前阶段

优先验证 Plan preflight repair：

- 预检阻断率
- 自动修复成功率
- 修订后 Plan 的需求覆盖率
- 修订后是否进入 Worker
- Plan 修订成本
- 修订后人工介入时间
- 验证命令拒绝率

### M3 真实任务验证

每个真实任务应额外记录：

- 是否触发 Plan preflight repair
- Plan 修订次数
- 修订原因和影响范围
- 修订后是否通过预检
- 是否需要人工修改 Plan
- 最终 Accepted Delivery
- 额外成本
- 人工介入分钟数
- 是否出现需求覆盖下降
- 同类错误是否复发

建议使用配对实验：

```text
基线组：关闭 plan_feedback / 自动局部重规划
实验组：开启受控能力
```

比较：

- Accepted Delivery Rate
- Cost per Accepted Delivery
- First-pass Rate
- Human Intervention Minutes
- Plan 修订成功率
- 失败复发率

### M3 之后

只有实验确认收益后，才考虑：

1. 局部一次性重规划
2. 基于历史经验的 KnowledgeStore
3. 受控策略重置
4. 更复杂的动态 Plan/DAG

Meta-Harness、ADAS、AFlow 等研究型能力暂不进入产品主线。

## 6. 产品决策建议

这份调研对 agent_go 的主要借鉴意义是：

1. Plan 应从普通文本输出升级为可验证的执行契约。
2. 执行反馈应回流，但必须按确定性问题、模型问题、基础设施问题和交付问题分层处理。
3. 执行前确定性修复优先于执行后自动重规划。
4. 跨任务经验必须隔离、可回滚、可验证。
5. 局部重规划优先于全局动态重规划。
6. Accepted Delivery 和人工成本优先于“系统自我进化程度”。
7. 在真实任务证据不足前，不引入 Meta-Harness 式自动自优化。

当前推荐路线：

```text
可靠 Plan 预检
  → 受控 Plan 修复
  → 可观测反馈
  → 真实任务 A/B 验证
  → 局部重规划
  → 再决定是否动态化
```

本讨论稿不改变当前 PRD、roadmap 或原调研文档，仅用于后续产品决策讨论。
